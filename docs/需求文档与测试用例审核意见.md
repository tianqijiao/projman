### 2.1 已修复：金额解析拒绝非有限数

严重程度：中

审核时发现 `_parse_float()` 已经能把 `abc` 这类非法金额转换成 400 错误，但没有拦截 Python 浮点解析中的特殊值：

- `inf`
- `-inf`
- `1e309`

这些值不会触发 `ValueError`，会被 `float()` 成功解析为正无穷或负无穷。手工提交这类金额后，项目可能保存成功。

影响：

- 台账页面可能显示 `inf`。
- Excel 导出时该值可能变成空值，造成页面与导出不一致。
- 预算合计、合同合计、差额等统计会变得不可解释。
- 当前非法金额测试只覆盖了 `abc`，没有覆盖非有限数。

已执行修改：

```python
import math


def _parse_float(value: str, field_label: str = "金额") -> float | None:
    value = value.strip()
    if not value:
        return None
    try:
        parsed = float(value)
    except ValueError:
        raise ValueError(f"{field_label}格式不正确") from None
    if not math.isfinite(parsed):
        raise ValueError(f"{field_label}格式不正确")
    return parsed
```

已补充测试：

```text
POST /projects，budget_amount=inf，应返回 400。
POST /projects，budget_amount=-inf，应返回 400。
POST /projects，budget_amount=1e309，应返回 400。
POST /projects/{id}/edit，contract_amount=inf，应返回 400。
POST /annual-executions/{id}/edit，budget_amount=inf，应返回 400。
```

处理状态：已按建议实现 `math.isfinite()` 校验，并补充 service 层和 Web 层测试。需求文档已明确“金额必须是有限数字”，测试计划已增加输入校验回归批次。

### 2.2 已修复：项目名称空白字符串绕过必填要求

严重程度：中

需求文档要求“新增项目至少需要填写年度和项目名称”。页面上项目名称输入框有 `required`，但 HTML `required` 只能拦截真正的空值，不能拦截只包含空格的字符串。

审核时 service 层创建项目直接保存：

```python
project = Project(
    year=year,
    name=name.strip(),
    budget_amount=budget_amount,
    notes=notes.strip(),

```

如果提交的 `name` 是 `"   "`，`name.strip()` 后会变成空字符串并被写入数据库。

影响：

- 台账中可能出现空项目名。
- 后续详情页、删除确认、附件归档等都依赖项目名称，体验会变差。
- 这与需求中“项目名称必填”的业务规则不一致。

已执行修改：

- 在 `create_project()` 中增加校验：`if not name.strip(): raise ValueError("项目名称不能为空")`。
- 在 `update_project()` 或项目编辑路由中也做同样校验，避免编辑时把名称改为空白。
- Web 层捕获该 `ValueError`，返回可理解的中文错误或重定向回表单。

已补充测试：

```text

当创建项目；
则系统拒绝保存，并返回中文错误；

```

建议至少覆盖：

- service 层：`create_project()` 拒绝空白名称。
- Web 层：`POST /projects` 提交空白名称不应 500，也不应创建记录。
- 编辑路径：`POST /projects/{id}/edit` 提交空白名称不应保存。

处理状态：已按上述建议实现并补充测试。需求文档已把“项目名称去除首尾空格后不能为空”列为服务端校验要求。

### 2.3 已修复：手工构造的金额和日期表单值不再触发 500

严重程度：中

审核时金额和日期解析函数如下：

```python
def _parse_float(value: str) -> float | None:
    value = value.strip()

        return None
    return float(value)
```

项目主档保存、年度执行保存、新增项目等路径都会调用这些函数。浏览器正常使用 `type="number"` 和 `type="date"` 时通常没问题，但只要手工构造请求、复制粘贴异常值，或绕过前端校验，就可能抛出 `ValueError`，导致 500。

相关入口包括：

- 新增项目：预算金额。
- 编辑项目主档：预算金额、合同金额、合同开始、合同结束。
- 编辑年度执行：年度预算、年度合同、验收日期、付款日期。

影响：

- 用户入口的异常输入没有被转换成可控错误。
- 原先自动化测试没有覆盖这类非法金额、非法日期。
- 这类问题在本地小工具中不是最高风险，但会影响稳定性和可解释性。

已执行修改：

- 新增安全解析函数，例如：

```python
def _parse_float_form(value: str, field_label: str) -> float | None:
    value = value.strip()
    if not value:
        return None
    try:
        return float(value)
    except ValueError:
        raise ValueError(f"{field_label}格式不正确")
```

```python
def _parse_date_form(value: str, field_label: str) -> date | None:
    value = value.strip()
    if not value:
        return None
    try:
        return date.fromisoformat(value)
    except ValueError:
        raise ValueError(f"{field_label}格式不正确")
```

- Web 路由统一捕获 `ValueError`，返回 400 或带错误提示的表单页面。
- 如果暂时不做完整表单回显，至少保证不会返回 500。

### 2.4 已修复：上传失败测试断言已收紧

处理状态：已将相关断言收紧为 `status_code == 400`。测试用例不再只验证“没有成功跳转”，而是锁定“受控失败”的响应契约。

### 8.2 P1 问题：PDF 识别链路尚未定义清楚

现状：

- 需求文档说支持合同 PDF，AI/API 可识别 PDF。
- 同时模型选择说明强调文本、图片理解能力，但没有明确 MVP 到底是：
  - 直接把 PDF 文件交给外部 API；
  - 本地提取 PDF 文本后发送文本；
  - 把 PDF 页面转为图片后发送；
  - 对扫描件走 OCR 或图像理解。
- 测试中 PDF 仅使用最小 fake 字节，能够验证流程，但不能约束真实 PDF 处理边界。

风险：

- 实现阶段会在“PDF 原文件上传给模型”和“本地解析后再调用模型”之间摇摆，影响依赖、性能、错误处理和隐私边界。
- 加密 PDF、扫描 PDF、超大 PDF、空文本 PDF 的用户提示可能没有统一规则。
- 如果模型接口实际不支持直接 PDF 输入，用例仍可能全部通过，但真实功能不可用。

建议：

- 需求中明确 MVP 的 PDF 处理策略，例如“优先本地提取文本；文本为空时提示用户改传图片或后续版本支持页面转图”。
- 明确不支持或暂缓支持的 PDF 类型：加密 PDF、超大 PDF、多合同合并 PDF、扫描件 OCR。
- 测试用例补充：
  - PDF 解析为空时显示中文错误或降级提示，不创建项目。
  - 超过大小限制的 PDF 被拒绝，且不调用 AI。
  - fake client 接收到的是规范化后的输入对象，而不是未定义格式的原始文件。

### 11.1 P1：归档失败会留下半成功项目

位置：

- `app/main.py` 的 `confirm_ai_project_draft()`，约第 356 至 392 行。
- `app/ai_project.py` 的 `extract_pdf_text()`，约第 201 至 208 行。

问题：

- 确认草稿时，代码先调用 `create_project()` 和 `update_project()` 创建正式项目，再尝试把原 PDF 归档为正式附件。
- 如果附件归档阶段失败，接口返回 `400`，但项目已经写入数据库，草稿仍保持 `pending` 且 `project_id` 为空。
- 同时 `extract_pdf_text()` 在 PDF 解析异常时会回退为 `content.decode(...)`。这会让损坏或伪造的 `.pdf` 文件只要字节可解码，就可能继续调用 AI 并创建草稿，和“PDF 损坏或解析失败时不调用 AI/API、不创建草稿”的需求不一致。

复现探针结果：

```text
draft    -> 303 /ai-projects/drafts/1
confirm  -> 400 只支持上传 PDF 文件
projects -> 1
attachments -> 0
draft_status -> pending
project_id -> None
```

风险：

- 用户看到确认失败，但数据库里已经多了一个正式项目。
- 后续再次确认同一草稿可能继续创建重复或不一致数据。
- 损坏 PDF 本应在识别前被拦截，却可能进入 AI 调用流程。

建议：

- `extract_pdf_text()` 解析异常时不要回退读取原始字节，应返回空文本或抛出可控异常，由路由返回“PDF 解析失败”。
- 测试中的 fake PDF 场景继续通过 `app.state.ai_pdf_text_extractor` 注入 fake extractor，不要依赖损坏 PDF 的 decode 回退。
- 确认创建前先完成可归档 PDF 的读取与基础校验，或把“创建项目 + 更新合同 + 保存附件 + 标记草稿 created + 清理临时文件”收敛到一个失败可回滚的事务边界。
- 补一个回归用例：归档失败时不得创建项目、不得标记草稿 created，并保留或清理临时文件的行为要明确。

### 11.2 P2：禁用态只在未注入 client 时阻断，测试成功路径没有覆盖真正启用态

位置：

- `app/main.py` 的 `create_ai_project_draft_route()`，约第 211 至 218 行。
- `tests/test_ai_project.py` 多数成功路径通过 `client.app.state.ai_project_client = FakeAiProjectClient(...)` 注入 fake client。

问题：

- 当前逻辑是：如果 `settings.enabled` 为 `true` 且没有 key，则返回配置错误；如果已经注入 `app.state.ai_project_client`，则即使 `PROJMAN_AI_ENABLED=false`，也可以继续创建 AI 草稿。

风险：

- 禁用态测试只覆盖 GET 页面提示，没有覆盖 POST 识别被拒绝。

- 成功路径测试显式设置 `PROJMAN_AI_ENABLED=true`，并通过 fake client 避免真实 API 调用；需要时设置 dummy key，确保不会读取真实凭据。

## 16. AI PDF 识别失败与进度提示修复记录

修复日期：2026-05-26

触发问题：

- 用户上传 PDF 后页面显示“识别失败，可重试或手工新建”，但没有具体原因。
- 点击“开始识别”后页面没有进度反馈，用户容易误以为没有响应或重复点击。

排查结论：

- 使用合成 PDF 直接调用当前 AI 配置验证，小图 PDF 图片路径可正常返回结构化字段，说明 AI 配置、模型和基本图片输入链路可用。
- 真实合同 PDF 更可能因为扫描页转 PNG 后体积偏大、页数偏多、服务端拒绝请求，或模型返回格式异常而失败；旧路由把这些异常统一吞成笼统提示，用户无法判断下一步该压缩 PDF、检查 Key，还是稍后重试。

### 20.1 P2：仅依赖进程环境变量的 API Key 可能被设置页保存覆盖为空

位置：

- `app/main.py` 的 `_save_ai_settings_from_form()`，约第 1268 至 1297 行。

问题：

- 如果当前进程通过环境变量 `PROJMAN_AI_API_KEY` 提供 key，且本项目 `.env` 里还没有 `PROJMAN_AI_API_KEY`，设置页在 AI 启用状态下提交空的 `ai_api_key` 时，代码会因为 `current_settings.api_key` 存在而允许保存。
- 但实际写入 `.env` 的 `PROJMAN_AI_API_KEY` 是空字符串，并同步写入 `app.state.ai_env_overrides`。
- 下一次读取配置时，空 override 会覆盖进程环境变量，导致当前运行进程进入“AI 已启用但未配置 API key”的坏状态。

复现探针：

```text
save_status -> 303
PROJMAN_AI_ENABLED=true
PROJMAN_AI_API_KEY=
ai_post_status -> 400
AI 功能已启用，但未配置 API key
```

风险：

- 用户以为设置保存成功，但保存后 AI 立即不可用。
- 这个问题只在“key 来自进程环境变量、`.env` 尚未保存 key、用户清空 key 输入框仍保持启用”的边界出现，因此普通 happy path 测试不容易覆盖。

建议：

- 如果 AI 保持启用，`stored_api_key` 应优先继承 `new_api_key`、`.env` 既有 key、`current_settings.api_key` 三者之一；不要在有可用进程 key 时写入空 key。
- 或者更明确地规定：启用状态下提交空 key 必须返回 `400`，提示用户填写 API Key。
- 补充回归用例：只有进程环境变量提供 key 时，设置页提交空 key 不应把当前运行态覆盖成无 key。

### 20.2 P3：API Key 明文显示与隐私规则口径需要统一

位置：

- `app/templates/settings.html`，约第 40 至 52 行。
- `docs/AI新建项目需求文档.md` 的 AI 配置与日志隐私段落。

问题：

- 设置页目前明确写着“API Key 在本页明文显示”，并用 `type="text"` 输出 `ai_settings.api_key`。
- 需求文档同时仍保留“密钥不得写入需求文档、日志、测试快照、页面输出或导出文件”的通用隐私规则。

风险：

- 如果“设置页明文显示”是当前本地单用户工具的有意设计，那么需求文档应把这个例外写清楚，避免后续审核反复判定为泄漏。
- 如果不是有意设计，建议改为 password 输入框、默认空值或“已配置”状态，不在 HTML 中回显完整 key。

建议：

  - 保留明文显示：需求文档把“页面输出”限制改为“不在普通业务页面、日志和导出中输出；设置页按本地工具偏好明文展示”。
